# Terraform Interview Questions & Answers

> Simple, practical answers written the way you'd explain them in an actual interview — no unnecessary jargon.

## Section A: Core Conceptual Questions (New Set of 13)

### 1. Explain the Terraform lifecycle

Terraform lifecycle basically means the steps Terraform goes through from writing code to destroying infrastructure. The standard flow is:

1. **Write** — You write `.tf` configuration files describing the desired infrastructure.
2. **Init** (`terraform init`) — Downloads providers and sets up the backend.
3. **Plan** (`terraform plan`) — Shows what will be created, changed, or destroyed by comparing your code with the current state.
4. **Apply** (`terraform apply`) — Actually creates/updates the real infrastructure and updates the state file.
5. **Destroy** (`terraform destroy`) — Removes the infrastructure when no longer needed.

There's also a `lifecycle` block inside a resource (not to be confused with the overall workflow) which controls behavior like `create_before_destroy`, `prevent_destroy`, and `ignore_changes`.

---

### 2. What is a Terraform State File?

The state file (`terraform.tfstate`) is a JSON file where Terraform keeps a record of every resource it manages — its ID, attributes, and metadata. It acts like a "map" between your `.tf` code and the actual real-world resources. Terraform uses this file to figure out what already exists, what needs to change, and what needs to be deleted, during every `plan` and `apply`.

Without the state file, Terraform would have no idea what it created before, so it's one of the most critical files in any Terraform project.

---

### 3. How do you secure the Terraform State File?

Since the state file can contain sensitive data (passwords, keys, connection strings) in plain text, here's how we secure it:

- Store it in a **remote backend** (Azure Storage Account, AWS S3) instead of locally.
- Enable **encryption at rest** on the storage (SSE for S3, Storage Service Encryption for Azure Blob).
- Restrict access using **IAM policies / RBAC** — only specific users/service principals should read or write it.
- Enable **state locking** (DynamoDB for AWS, native lease-based locking for Azure Blob) to avoid two people applying at the same time.
- Enable **versioning** on the storage account/bucket so you can roll back if the state gets corrupted.
- Never commit `.tfstate` to Git.
- Use `sensitive = true` on variables/outputs so secrets don't get printed in the CLI output.

---

### 4. What is Terraform Refresh?

`terraform refresh` (now mostly done automatically as part of `plan`/`apply`, or via `terraform apply -refresh-only` in newer versions) syncs the state file with the real infrastructure. It checks the actual cloud resources and updates the state file to reflect their current real-world status — without changing any actual infrastructure. It's useful when someone changed something outside Terraform and you want your state file to reflect reality before planning further changes.

### 5. Write Terraform code to create an EC2 instance and Security Group

```hcl
provider "aws" {
  region = "ap-south-1"
}

resource "aws_security_group" "web_sg" {
  name        = "web-sg"
  description = "Allow SSH and HTTP"

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "web-sg"
  }
}

resource "aws_instance" "web_server" {
  ami                    = "ami-0abcdef1234567890" # replace with a valid AMI ID
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.web_sg.id]

  tags = {
    Name = "web-server"
  }
}
```

This creates a security group allowing SSH (22) and HTTP (80), then attaches it to an EC2 instance.

### 6. What is Terraform Drift?

Drift happens when the actual state of your infrastructure (in the cloud) no longer matches what's recorded in the Terraform state file. This usually happens when someone manually changes a resource in the AWS/Azure portal or CLI instead of going through Terraform — for example, someone manually adds a tag or resizes a VM directly on the portal.

---

### 7. How do you identify and resolve Terraform Drift?

**To identify drift:**
- Run `terraform plan`. If it shows changes even though you haven't touched the `.tf` files, that means drift has occurred.
- You can also run `terraform refresh` (or `apply -refresh-only`) to sync the state with real infra and see the diff.

**To resolve drift:**
- If the manual change is acceptable, update your `.tf` code to match reality, then run `terraform apply` so state, code, and real infra all align again.
- If the manual change is NOT acceptable, run `terraform apply` as-is — Terraform will revert the resource back to what's defined in code.
- For minor things you want to permanently ignore (like tags added by another team), use the `lifecycle { ignore_changes = [...] }` block.

---

### 8. What is terraform fmt?

`terraform fmt` is a formatting command. It automatically rewrites your `.tf` files into the standard Terraform style — consistent indentation, spacing, and alignment. It doesn't change any logic, just makes the code look clean and consistent, which is very helpful when multiple people are working on the same codebase.

---

### 9. Difference between Resource and Data Source

| | Resource | Data Source |
|---|---|---|
| Purpose | Creates/manages a new infrastructure object | Reads/fetches info about an existing object (not managed by this Terraform) |
| Syntax | `resource "type" "name" { ... }` | `data "type" "name" { ... }` |
| Lifecycle | Terraform owns create/update/destroy | Read-only, Terraform doesn't manage it |
| Example | `resource "aws_instance" "web" {...}` creates a new EC2 | `data "aws_ami" "latest" {...}` fetches the latest AMI ID to use in a resource |

In short: **resource = create something new**, **data source = look up something that already exists**.

### 10. How do you secure passwords and secrets in Terraform?

- Never hardcode secrets in `.tf` files.
- Use a **secrets manager** — AWS Secrets Manager, AWS SSM Parameter Store, Azure Key Vault, or HashiCorp Vault — and reference secrets using a `data` source at runtime.
- Mark sensitive variables/outputs with `sensitive = true` so they're hidden in CLI/plan output.
- Pass secrets via **environment variables** (`TF_VAR_xxx`) instead of putting them in `.tfvars` files.
- If you must use `.tfvars` for secrets, add it to `.gitignore` and never commit it.
- Keep the remote state encrypted, since resource attributes (including secrets passed as arguments) get stored in state too.
- Use CI/CD secret stores (GitHub Actions secrets, Azure DevOps variable groups) to inject values during pipeline runs instead of storing them anywhere in the repo.

### 11. Which Terraform Provider version are you using?

This is something you should answer based on your actual project — check your `versions.tf` or `required_providers` block, e.g.:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.90"
    }
  }
  required_version = ">= 1.5.0"
}
```

In an interview, mention the actual version you used on your project (e.g., "we pinned `azurerm` to `~> 3.x` and Terraform core to `1.6`") and explain that you pin versions to avoid breaking changes when providers release new major versions.

### 12. Why do you use remote backend for Terraform state?

- **Team collaboration** — everyone works off the same state file instead of local copies going out of sync.
- **State locking** — prevents two people from running `apply` at the same time and corrupting state.
- **Durability & versioning** — cloud storage (S3, Azure Blob) is far safer than someone's laptop; you also get version history to roll back.
- **Security** — centralized access control (IAM/RBAC) instead of a file sitting on individual machines.
- **CI/CD friendly** — pipelines can access the same state without needing to move files around manually.

---

### 13. How do you implement state locking in Terraform?

State locking prevents concurrent operations from corrupting the state file.

- **AWS**: Use an S3 backend along with a **DynamoDB table** for locking:
```hcl
terraform {
  backend "s3" {
    bucket         = "my-tfstate-bucket"
    key            = "prod/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```
- **Azure**: The `azurerm` backend (Storage Account + Blob container) has native lease-based locking built in — no extra table needed:
```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "tfstateaccount"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}
```

When someone runs `apply`, Terraform acquires a lock; if another person tries to run `apply` simultaneously, they get an error saying the state is locked, until the first operation finishes.

## Section B: Original Question Bank (54 Questions)

### 1. What is Terraform taint?

`terraform taint` marks a resource in the state as "tainted," meaning Terraform will destroy and recreate it on the next `apply`, even if no configuration changed. It's useful when a resource is behaving oddly (e.g., a VM got corrupted) and you want to force a clean recreation. In newer Terraform versions, this is done via `terraform apply -replace="resource.address"` instead of the older `taint` command.

### 2. How do you detect the drift?

Run `terraform plan`. If it shows a diff even though your `.tf` files haven't changed, that's drift — someone changed the actual resource outside of Terraform. You can also do `terraform apply -refresh-only` to explicitly sync and inspect what changed.

### 3. What are the services/things you have configured using Terraform?

This is a personal/project-based answer. Common example: "I've used Terraform to provision VNets/VPCs, subnets, NSGs/Security Groups, VMs/EC2 instances, Storage Accounts/S3 buckets, App Services/Lambda, AKS/EKS clusters, Azure SQL/RDS databases, Load Balancers, and IAM roles/RBAC assignments — along with setting up remote backends and CI/CD pipelines for Terraform deployments."

### 4. How do you handle if your Terraform state file is exposed to public and if they make any changes or if they hack anything which is there in Terraform state file?

- Immediately restrict/revoke public access to the storage account/bucket.
- Rotate any secrets/credentials that were exposed in the state (assume they're compromised).
- Check access logs to see what was read/changed.
- Restore the state file from a previous version (since versioning should be enabled).
- Run `terraform plan` to check for unexpected drift caused by unauthorized changes, and re-apply from your source-controlled code to bring infra back to the desired state.
- Going forward, enable encryption, private access only, RBAC/IAM restrictions, and state locking to prevent recurrence.

### 5. What is Resource Block & Output block in Terraform?

- **Resource block**: Defines an infrastructure object to create/manage, e.g. `resource "aws_instance" "web" { ami = "..." instance_type = "t2.micro" }`.
- **Output block**: Used to display or export values after apply, e.g. `output "instance_ip" { value = aws_instance.web.public_ip }`. Outputs are useful for showing key info in the CLI or passing values between modules.

### 6. What is module in Terraform and did you write any modules? If yes, what are those & can you explain them?

A module is a reusable, self-contained package of `.tf` files that can be called multiple times with different inputs — like a function in programming. On projects, common modules I've written/used: a **networking module** (VNet/subnet/NSG), a **VM/App Service module**, and a **storage module**. Each takes input variables (like environment name, size, region) and outputs things like resource IDs, so the same module can be reused across dev/test/prod.

### 7. When do you use for_each, count & for loop in Terraform?

- **count**: When you need multiple identical copies of a resource, indexed numerically (e.g., `count = 3` creates 3 VMs referenced as `[0]`, `[1]`, `[2]`).
- **for_each**: When you need multiple resources based on a map or set of strings, each with a distinct key — safer than `count` because adding/removing an item doesn't shift indexes of others.
- **for loop**: Used inside expressions (not resource blocks directly) to transform lists/maps, e.g., building a list of subnet names or generating a map from a variable.

### 8. Can you please explain any Resource block in Terraform?

Example:
```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "my-app-logs-bucket"
  tags = {
    Environment = "prod"
  }
}
```
Here, `aws_s3_bucket` is the resource type, `logs` is the local name Terraform uses to refer to it internally, and inside the block we define the actual configuration (bucket name, tags, etc.).

### 9. What are Terraform functions?

Built-in functions used inside expressions to manipulate data — since Terraform doesn't allow user-defined functions. Categories include: string functions (`join`, `split`, `lower`, `format`), numeric functions (`min`, `max`, `ceil`), collection functions (`length`, `merge`, `lookup`, `concat`), and type conversion functions (`tostring`, `tolist`). Example: `join(",", ["a","b","c"])` gives `"a,b,c"`.

### 10. What are modules in Terraform?

(Same concept as Q6) Modules are reusable groups of Terraform configuration files that can be called with different inputs to avoid repeating code. There's always a "root module" (your main working directory), and you can call "child modules" from it.

### 11. How do you call the existing config like a child module in Terraform?

```hcl
module "networking" {
  source              = "./modules/networking"
  vnet_name           = "prod-vnet"
  address_space       = ["10.0.0.0/16"]
}
```
`source` points to the module's location (local path, Git repo, or Terraform Registry), and you pass required input variables. You access its outputs elsewhere as `module.networking.subnet_id`.

### 13. Explain core Terraform end-to-end workflow to deploy and delete resources in Azure?

1. Write `.tf` files with `azurerm` provider config.
2. `terraform init` — downloads the azurerm provider, configures the backend (e.g., Azure Storage for state).
3. `terraform plan` — shows what will be created in Azure.
4. `terraform apply` — creates the resource group, VNet, VMs, etc., in Azure and records them in state.
5. To delete: `terraform destroy` (or remove specific resource blocks and `apply`) — Terraform calls Azure APIs to delete those resources and updates state accordingly.

### 14. We have existing Terraform infrastructure created in Azure cloud, now one particular resource needs to be re-created whenever we do the next Apply?

Use `terraform apply -replace="azurerm_resource_type.name"` (in older versions, `terraform taint azurerm_resource_type.name`). This forces Terraform to destroy and recreate just that resource on the next apply, without touching anything else.

### 15. Explain or walk-through step by step process to secure .tfstate file and by making it readily available for other developers within the team?

1. Create an Azure Storage Account + Blob Container (or S3 bucket) dedicated to state storage.
2. Enable encryption at rest and enable versioning/soft delete.
3. Restrict access using RBAC/IAM — only the DevOps team/service principal gets access.
4. Configure the `azurerm`/`s3` backend block in your Terraform code pointing to this storage.
5. Enable state locking (native in Azure Blob, DynamoDB table for S3).
6. Team members run `terraform init` — they automatically pull the shared state, no manual file copying needed.
7. Set up CI/CD (Azure DevOps/GitHub Actions) with proper access to run plan/apply against this shared backend.

### 16. Can you please explain how do you import the existing Azure cloud infrastructure & explain that block clearly?

We use `terraform import` to bring an existing manually-created resource under Terraform management.

```hcl
resource "azurerm_storage_account" "existing_sa" {
  name                     = "existingstorageacct"
  resource_group_name      = "rg-existing"
  location                 = "centralindia"
  account_tier             = "Standard"
  account_replication_type = "LRS"
}
```
Then run:
```
terraform import azurerm_storage_account.existing_sa /subscriptions/<sub-id>/resourceGroups/rg-existing/providers/Microsoft.Storage/storageAccounts/existingstorageacct
```
This links the existing Azure resource ID to the Terraform resource block in state. Note: import only updates the state file — you still need to manually write the matching `.tf` configuration so `plan` shows no diff afterward.

### 17. Explain the various types of Meta-Arguments in Terraform and their benefits?

- **count** — create multiple instances of a resource based on a number.
- **for_each** — create multiple instances based on a map/set, each with a unique key.
- **depends_on** — explicitly define dependency between resources when Terraform can't infer it automatically.
- **lifecycle** — controls behaviors like `create_before_destroy`, `prevent_destroy`, `ignore_changes`.
- **provider** — specify which provider configuration (alias) a resource should use, useful in multi-region/multi-account setups.

Benefit: they give fine control over how resources are created, replaced, or tied to one another, without duplicating code.

### 18. Who creates the terraform.tfstate.backup file and under which scenario it is created?

Terraform itself creates `terraform.tfstate.backup` automatically, right before it overwrites the existing state file during an `apply`. It's essentially a safety copy of the previous state, so if something goes wrong during the apply, you have the last known-good state to fall back to.

### 19. Resource "Azure Storage Account" was previously created manually, now the resource needs to be brought under Terraform to manage & maintain. How do we achieve the same?

Same as Q16 — write a matching resource block for the Storage Account, then run `terraform import azurerm_storage_account.<name> <azure_resource_id>`. After import, run `terraform plan` to verify there's no diff between your written config and the actual resource; adjust the `.tf` code until plan shows no changes.

### 20. Resource "Azure App Service" was created and managed by Terraform, but someone added a few tags or made minor changes manually on the portal — what will happen in such cases? How will Terraform react to such changes?

Next time you run `terraform plan`, Terraform will detect that the actual resource differs from state (drift) and show the manual changes as something it plans to "correct." If you run `apply`, Terraform will revert those manual tags/changes back to what's defined in the `.tf` code — unless you've added those attributes to `lifecycle { ignore_changes = [...] }`, in which case Terraform will ignore them permanently.

### 21. Recently migrated state file to Azure Storage (blob), now post Terraform configuration change I don't see any .tfstate.backup file getting created locally or remotely?

That's expected behavior — the local `.tfstate.backup` mechanism only applies to the **local backend**. Once you migrate to a remote backend like Azure Blob, Terraform relies on the backend's own versioning/history feature instead of creating a local backup file. To get "backup" protection with a remote backend, you should enable **blob versioning** or **soft delete** on the Storage Account so you can recover previous state versions from there.

### 22. Assume Terraform configuration files are deleted, and I am just left with an updated .tfstate file. How do we recover the configuration using a .tfstate file, if possible?

You can't perfectly regenerate the exact original `.tf` files (comments, variable names, structure are lost), but you can rebuild working configuration by:
- Using `terraform show` or `terraform state list` / `terraform state show <resource>` to inspect each resource's current attributes recorded in state.
- Manually writing new `.tf` resource blocks that match those attributes.
- Alternatively, for cloud-native regeneration, tools like `terraformer` can auto-generate `.tf` files directly from existing cloud resources (not from the state file itself).
- Run `terraform plan` afterward and keep adjusting until there's no diff, meaning your recreated code matches the state/actual resources.

### 23. What is Terraform workspace and how it is beneficial in day-in-day-out jobs?

A workspace lets you maintain multiple separate state files using the same set of `.tf` configuration files — commonly used for managing dev/test/prod environments without duplicating code. E.g., `terraform workspace new dev`, `terraform workspace select prod`. Benefit: You avoid copy-pasting the same code for each environment; you just switch workspace and each maintains its own isolated state.

### 24. What will you do if the Terraform state file gets corrupted?

- Stop making any further changes immediately.
- Restore from the latest backup — either the automatic `.tfstate.backup`, or a previous version from remote backend versioning (S3 versioning / Azure Blob versioning).
- If no backup exists, manually rebuild state using `terraform import` for each resource one by one.
- Validate with `terraform plan` to ensure the restored/rebuilt state matches actual infrastructure with no unexpected diff.

### 25. What are all the Terraform functions have you used?

Commonly used ones on real projects: `lookup()`, `merge()`, `join()`, `split()`, `format()`, `length()`, `element()`, `concat()`, `coalesce()`, `try()`, `tostring()`, `tomap()`, `cidrsubnet()`, `file()`, and `templatefile()`.

### 26. What is Terraform import?

`terraform import` is a command used to bring existing infrastructure (created outside Terraform, e.g. manually via portal/CLI) under Terraform's management by adding it to the state file. You still need to write a matching resource block in code; import only updates state, not the `.tf` files.

### 27. What is Terraform taint?

(Duplicate of Q1) Marks a resource so it gets destroyed and recreated on the next apply. Modern equivalent: `terraform apply -replace="resource.address"`.

### 28. How to convert existing Azure resource to Terraform code?

- Manually write the resource block matching the existing resource's properties, then `terraform import` it — this is the standard/manual approach.
- Or use automated tools like **Azure Export for Terraform (`aztfexport`)**, which scans existing Azure resources/resource groups and generates both the `.tf` code and the state automatically, saving a lot of manual effort.

### 29. Write a Terraform import command for VM resource?

```
terraform import azurerm_virtual_machine.my_vm /subscriptions/<subscription-id>/resourceGroups/<rg-name>/providers/Microsoft.Compute/virtualMachines/<vm-name>
```
For AWS EC2:
```
terraform import aws_instance.my_vm i-0123456789abcdef0
```

### 30. What is/are Terraform modules?

(Same as Q6/Q10) Reusable, self-contained sets of Terraform configuration that accept input variables and produce outputs — used to avoid duplicating code across environments/projects.

### 31. What is resource type & data source type in Terraform?

- **Resource type**: e.g., `aws_instance`, `azurerm_storage_account` — defines what kind of object Terraform will create and manage.
- **Data source type**: e.g., `data "aws_ami"`, `data "azurerm_resource_group"` — defines what kind of existing object Terraform will read/query (read-only, not managed).

### 32. Where do you store your Terraform state file?

In a **remote backend** — commonly Azure Storage Account (Blob container) for Azure projects, or AWS S3 bucket (with a DynamoDB table for locking) for AWS projects. This is preferred over local storage for team collaboration, locking, and security.

### 33. How many backend types are there to store Terraform state file?

Terraform supports several backend types, including: `local`, `s3` (AWS), `azurerm` (Azure Blob), `gcs` (Google Cloud Storage), `remote`/`cloud` (Terraform Cloud/HCP Terraform), `consul`, `kubernetes`, `etcd`, `http`, and `pg` (Postgres). In practice, most teams use `s3`, `azurerm`, or Terraform Cloud.

### 34. How many ways we can pass variables in Terraform?

- Command line flag: `-var="key=value"`
- Variable definition files: `terraform.tfvars` or `*.auto.tfvars`
- Environment variables: `TF_VAR_key=value`
- Interactive prompt (if a required variable isn't supplied, Terraform asks for it)
- Default values defined directly in the `variable` block

### 35. How many types of provisioners are there in Terraform?

Three main types: **local-exec** (runs a command on the machine running Terraform), **remote-exec** (runs a command on the newly created remote resource, e.g., via SSH), and **file** (copies files from local machine to the remote resource). Note: HashiCorp recommends provisioners as a last resort — prefer native tools like cloud-init, user_data, or configuration management tools (Ansible) instead.

### 36. How do you debug Terraform issues?

- Set `TF_LOG=DEBUG` (or `TRACE`, `INFO`, `WARN`, `ERROR`) environment variable to get detailed logs.
- Use `terraform validate` to catch syntax/config errors.
- Use `terraform plan` output carefully to see exactly what's changing.
- Use `terraform show`/`terraform state list` to inspect current state.
- Check provider-specific error messages (they usually point to the exact API error from AWS/Azure).
- Use `terraform console` to test expressions interactively.

### 37. What is Terraform output block?

An `output` block is used to display specific values after `apply`, or to expose values from a module to whoever calls it. Example:
```hcl
output "vm_public_ip" {
  value = azurerm_public_ip.example.ip_address
}
```

### 38. What is terraform init?

`terraform init` is the first command run in any Terraform project/directory. It downloads the required providers, initializes the backend (connects to remote state storage), and sets up modules referenced in the code. It must be run again whenever you change providers, backend config, or add new modules.

### 39. What is a Terraform null resource?

`null_resource` is a resource that doesn't correspond to any real infrastructure — it's mainly used as a placeholder to run provisioners (like `local-exec`) or to trigger actions based on changes in other resources, using the `triggers` argument. Example use case: running a script whenever an EC2 instance ID changes.

### 40. What happens if a state file is lost?

Terraform loses track of everything it previously created — the next `plan`/`apply` will think none of the resources exist and try to recreate everything from scratch, potentially causing duplicate resources or conflicts (e.g., "resource already exists" errors). Recovery involves restoring from backup/versioning, or manually re-importing every resource one by one using `terraform import`.

### 41. How do you delete a specific resource in Terraform?

Two approaches:
- Remove the resource block from your `.tf` file, then run `terraform apply` — Terraform will detect it's no longer in config and destroy it.
- Or run `terraform destroy -target="resource_type.name"` to destroy just that one resource without touching the code (use `-target` carefully — it's meant as an exception, not routine use).

### 42. How do you detect if there is drift in Terraform?

(Same as Q2) Run `terraform plan` — any unexpected diff means drift. `terraform apply -refresh-only` explicitly refreshes and shows drift without applying changes.

### 43. How do you import the resource which has been configured manually under Terraform management?

(Same approach as Q16/Q19) Write a matching resource block, then run `terraform import <resource_type>.<name> <cloud_resource_id>`, and adjust the config until `terraform plan` shows no differences.

### 44. You want to run specific scripts after provisioning resources with Terraform — how would you achieve this and what provisioner might you use?

Use a `remote-exec` provisioner (runs the script on the newly created resource, e.g., via SSH/WinRM) or `local-exec` (runs a script locally on the machine executing Terraform). Example:
```hcl
resource "aws_instance" "web" {
  # ... config ...

  provisioner "remote-exec" {
    inline = [
      "sudo apt update",
      "sudo apt install -y nginx"
    ]
  }
}
```
Better practice for real production use: use `user_data` (cloud-init) or a proper config management tool instead of provisioners, since provisioners are considered a last resort by HashiCorp.

### 45. Explain provisioners in Terraform?

Provisioners let you execute scripts or commands as part of resource creation/destruction, for tasks Terraform can't natively handle (like bootstrapping software inside a VM). Types: `local-exec`, `remote-exec`, and `file`. They're seen as a "last resort" because they introduce imperative logic into Terraform's otherwise declarative model, and Terraform can't guarantee/track their success reliably.

### 46. You are dealing with sensitive information such as API keys, passwords in your Terraform configuration — what approach could you take to manage their configuration?

(Same approach as Q10) Use a secrets manager (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault) and reference secrets via data sources at runtime; mark variables `sensitive = true`; avoid hardcoding or committing secrets; pass via environment variables or pipeline secret stores; keep state encrypted since secrets often end up recorded there too.

### 47. What are the key components of a Terraform configuration file?

- **Provider block** — declares which cloud/platform to talk to.
- **Resource block** — defines infrastructure to create.
- **Data block** — reads existing infrastructure/data.
- **Variable block** — defines input parameters.
- **Output block** — exposes values after apply.
- **Module block** — calls reusable configuration.
- **Terraform block** — sets required providers, required Terraform version, and backend config.

### 48. What is a Terraform provider and how does it facilitate platform interaction?

A provider is a plugin that lets Terraform talk to a specific platform's API — e.g., the `aws` provider talks to AWS APIs, `azurerm` talks to Azure Resource Manager APIs. It translates your `.tf` resource definitions into actual API calls (create/update/delete) against that platform, and also handles reading back current resource state.

### 49. What is the difference between Terraform local-exec and remote-exec provisioners?

- **local-exec**: Runs a command on the machine where Terraform itself is being executed (your laptop/CI runner) — e.g., logging output, calling a local script.
- **remote-exec**: Runs a command on the newly created remote resource itself (via SSH for Linux or WinRM for Windows) — e.g., installing software on a freshly created VM.

### 50. Junior DevOps engineer accidentally deleted the state file — what steps would we take to recover it?

1. Check if the remote backend has versioning enabled (S3 versioning / Azure Blob versioning/soft-delete) — restore the last good version from there.
2. If a local `.tfstate.backup` exists, rename it back to `terraform.tfstate`.
3. If no backup exists anywhere, rebuild state manually using `terraform import` for every existing resource, one at a time.
4. After recovery, run `terraform plan` to confirm state now matches real infrastructure with no unwanted diff.
5. Going forward, enable backend versioning and restrict delete permissions to prevent recurrence.

### 52. What are local variables in Terraform?

Local values (`locals` block) let you define a named expression once and reuse it multiple times within your configuration, mainly to avoid repeating complex expressions. Example:
```hcl
locals {
  common_tags = {
    Environment = "prod"
    Team        = "devops"
  }
}

resource "aws_instance" "web" {
  # ...
  tags = local.common_tags
}
```
Unlike variables, locals aren't set externally — they're computed within the configuration itself.

### 53. What is a dynamic block in Terraform?

A `dynamic` block lets you generate repeated nested blocks (like multiple `ingress` rules inside a security group) programmatically from a list/map, instead of writing each one manually. Example:
```hcl
resource "aws_security_group" "example" {
  name = "dynamic-sg"

  dynamic "ingress" {
    for_each = var.allowed_ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```
This generates one `ingress` sub-block per port in `var.allowed_ports`.

### 54. How do you import an existing Terraform infrastructure?

(Same as Q16/Q19/Q43) Write a matching resource block in your `.tf` code, then run `terraform import <resource_type>.<local_name> <cloud_resource_id>` to link the real resource to Terraform's state. Follow up with `terraform plan` repeatedly, adjusting your config, until there's no drift shown — meaning the written configuration accurately reflects the imported resource.
